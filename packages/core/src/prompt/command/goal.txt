OpenCode goal mode command "/goal" was invoked.

Arguments:
<goal_command_arguments>
$ARGUMENTS
</goal_command_arguments>

Use the goal tools to handle this command:

- If the arguments are empty, call get_goal and briefly report the current goal state.
- If the arguments are "status", "show", or "current", call get_goal and briefly report the current goal state.
- If the arguments are "history", call get_goal_history and briefly report the current goal history.
- If the arguments are "clear", "stop", "off", "reset", "none", or "cancel", call clear_goal and report whether a goal was cleared.
- If the arguments are "pause", pause the current goal by calling update_goal_status with status "paused" and report the result.
- If the arguments are "resume", resume a paused goal by calling update_goal_status with status "active" and continue working toward it. A limited goal must be extended first; do not claim resume bypasses a limit.
- If the arguments start with "extend ", explicitly extend a limited goal by calling extend_goal with the higher limits named in the arguments. Pass null for every limit the user did not name, so an extended goal is unlimited unless the user gives real numbers. Extending reactivates the goal only when the new limits actually admit its recorded usage; if it reports that usage still exceeds a limit, tell the user which limit is still exhausted instead of claiming the goal resumed.
- If the arguments start with "edit ", update the current goal objective by calling update_goal_objective with the remaining text. Pass a new title as well when the remaining text implies a different short label for the status bar; omit it to keep the current one.
- If the arguments start with "complete " or "done ", perform a completion audit against real artifacts and command output. Call update_goal with status "complete" only if the goal is achieved, using concise evidence from the audit.
- If the arguments start with "unmet ", "blocked ", or "blocker ", call update_goal with status "unmet" only when the goal cannot be achieved or needs external input, using the remaining arguments as the blocker.
- Otherwise, create a new goal with create_goal. Do not use the arguments verbatim as the objective. Put in the objective the outcome to reach, plus anything a later turn could not cheaply re-derive from the repo - the user's intent, a constraint, a decision already made - and leave the backlog out: per-item instructions and acceptance detail belong in the first turn's plan, where they cost one turn instead of every turn. Neither length nor brevity is the point; saying only what is needed is. Pass the same work as a title of a few words: that is the one-line label the session status bar shows, and without one the bar has to fall back to the objective. Goals are unlimited by default: when the user does not name explicit numbers, pass token_budget: null, max_auto_turns: null, and max_duration_seconds: null to create_goal, where null means no cap at all. Only pass a number for a limit the user actually asked for; if the user includes explicit budget instructions in words, pass the matching limit to create_goal rather than leaving those words in the objective. If the user asks you to formulate the goal yourself rather than giving you the wording, use set_goal instead.

- For an unattended or overnight run, also raise the self-pausing tolerances when the user says the work must keep going without supervision, or when they describe being away for hours: pass max_prompt_failures (consecutive failed auto-continue prompts tolerated before the goal pauses) and max_no_progress_turns (consecutive low-output turns tolerated before the goal pauses) to create_goal. Both default low (3 and 2), so an unattended goal otherwise pauses itself on the first quiet stretch or a transient provider failure while nobody is watching. Lower no_progress_token_threshold only when single turns are legitimately long (a big build or test run) and you want those not to count as stalls: it is the floor a turn must clear to count as progress, so raising it would make exactly those long quiet turns count as stalls. Leave all three unset when the user did not ask for an unattended run - the defaults are the right guardrails for supervised work.

Create a goal only from these explicit command arguments. Do not infer a goal from unrelated session context. After create_goal succeeds, continue working toward the new goal.
